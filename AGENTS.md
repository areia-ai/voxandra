# Voxandra Agent Guide

Use this file as the current operational guide for coding agents working in this repo. Older planning docs are still useful for context, but the app has moved well past the initial mock-data phase. When docs conflict, prefer the current source code and the most recent entries in `LOG.md`.

## Maintainer-Private Files

This guide refers to some documents that are not in the public repository: `LOG.md` (the working log), `AGENTIC_FUTURE.md`, `PRICING_RATIONALE.md`, `ROADMAP.md`, `PRODUCT_BRIEF.md`, the older planning docs, and `AGENTS.local.md`. The maintainers keep them in a private overlay, and `.gitignore` blocks them here. In a public clone they are absent: rely on this file and the source code, and skip any step that says to read or update them. If you do have them, never commit them to this repository.

## Project Snapshot

- Voxandra is a Next.js App Router SaaS for multilingual business calls. It translates both sides of live phone conversations, provides private guidance while people talk, and turns each call into a reviewed Call Record.
- The current app is TypeScript, React, Tailwind CSS, Convex, Convex Auth, Twilio browser calling, Stripe billing/credits, and OpenAI extraction/transcription.
- Product analytics use PostHog EU Cloud through the browser SDK only; session replay, autocapture, server-side analytics, and customer-content capture are intentionally disabled for v1. DataFast was removed on 2026-10-08 (script, `@datafast/ai-crawl` crawler tracking, goal mirror, env var); do not reintroduce a second analytics vendor without explicit product direction.
- The public product position is an AI platform for multilingual business calls, led by Live Voice Translation. Avoid positioning it as a generic cheap-calling app, transcript-import product, or autonomous voice-agent platform.
- The authenticated dashboard should optimize post-call momentum: start a call, see processing status, then review AI note, transcript, contact cleanup, reminders, or all memory.

## Agentic Future Direction

- `AGENTIC_FUTURE.md` captures the long-term direction: Voxandra starts human-first, uses reviewed human call records as the learning and evaluation layer, and may later grow into supervised and then autonomous phone agents.
- Preserve the current human-first and review-first product path. Do not position the current product as an autonomous AI voice-agent platform.
- Live Voice Translation is the acquisition wedge and primary translated-call mode. The two-leg bridge, spoken disclosure, Guidance routing, translated-audio billing, and bilingual Call Record pipeline are implemented behind `REALTIME_VOICE_TRANSLATION_ENABLED`, paid-plan eligibility, and an owner-controlled workspace setting. **The global switch was opened in production on 2026-09-15** (Convex prod env and the VPS worker env together — see `LOG.md`; it is read in both places and must be changed in both, worker first when enabling, Convex first when disabling). The older workspace allowlists remain for private QA only. Public copy may now describe translated calls as available on every paid plan.
- The shared Palabra capability catalog in `scripts/translation-language-catalog.mjs` contains 48 documented bidirectional candidates, with stable stored codes and provider mappings at the worker boundary. Expansion is implemented but disabled by default until live acceptance: coordinate `PALABRA_EXPANDED_LANGUAGES_ENABLED` in worker/Convex and `NEXT_PUBLIC_PALABRA_EXPANDED_LANGUAGES_ENABLED` in the frontend build. Both selectors then offer the same 48 languages, including trials. Preserve legacy OpenAI restrictions. See `LANGUAGE_VALIDATION.md` and the runbook before activation.
- Existing common launch languages are English, Spanish, Portuguese, French, German, Italian, Russian, Hindi, Indonesian, Vietnamese, Korean, Japanese, and Chinese. Voice Translation requires an explicit caller/recipient pair; do not substitute automatic language detection for this v1 requirement.
- Future agent features should move through shadow, suggested-operator, supervised-mission, and autonomous stages. Any action that spends money, places calls, sends messages, updates important records, shares sensitive data, or contacts external parties needs approval gates unless explicit policy says otherwise.
- Reviewed edits, accepted suggestions, dismissed suggestions, and follow-up outcomes may become workspace-scoped evaluation examples. Do not export or use them for external model training without explicit customer consent and retention/deletion controls.
- Future agent learning should start with workspace-scoped retrieval over reviewed records, operational memory, and workspace policies. Do not introduce cross-customer learning, vendor training, fine-tuning, or external model training without explicit opt-in consent and deletion controls.
- `convex/agentLearning.ts` and `agentLearningExamples` are the first derived demonstration index for this path. Keep examples compact, workspace-scoped, review-derived, and excluded from raw-audio or external-training flows. Learning examples now carry realized outcomes: resolving a reminder or action item re-derives the originating call's examples (`refreshLearningExamplesForCall`), and retrieval is wired into the pre-call brief, dialer Call prep, and the live-guidance worker context via `findRelevantLearningExamples`.
- Shadow Agent v1 is implemented as internal-only infrastructure: after transcription, `convex/shadowAgent.ts` records an independent prediction as an `agentRunEvents` row (`prediction`, mode `agent_shadow`), and review accept/dismiss deterministically scores it (`convex/shadowAgentScoring.ts`) onto `shadowAgentRuns`. It never sees the extraction draft, takes no external action, and has no customer-facing UI — keep it that way without explicit product direction. Prompt changes must bump `SHADOW_AGENT_PROMPT_VERSION` in `src/lib/ai/shadow-agent-prompt.ts` and be logged in `LOG.md`. Env: `SHADOW_AGENT_ENABLED` (kill switch), `OPENAI_SHADOW_MODEL` (model override).
- DTMF keypad presses persist as workspace-scoped `callKeypadEvents` telemetry (IVR-path signal for future agents). Digits in rapid runs beyond 3 presses are stored masked (`•`) because keypads carry PINs/account numbers; keypad data must never reach PostHog or any other analytics tool.
- Translated calls default to a 30-minute hard limit; workspace owners can select 30, 45, or 60 minutes in Settings. New calls snapshot that limit; credit affordability and operator ceilings can only shorten it. The worker's speech-based inactivity policy warns at two minutes and ends both legs at three, starting after connection/disclosure. The originating caller's Keep connected acknowledgement resets inactivity only, never the hard limit or reservation. Keep all of these independent safeguards. See `REALTIME_WORKER_RUNBOOK.md` for the coordinated rollout, VAD dependency, and live-audio acceptance requirements; the production test cap is not removed by a source change alone.
- The provider-neutral realtime runtime foundation lives in `convex/realtimeRuntime.ts` and the related schema tables. Treat it as infrastructure for future workers and gated product surfaces, not as permission to expose autonomous calling in customer UI.
- Translated-call startup uses `BridgeIntroduction` in `scripts/realtime-media-worker-disclosures.mjs`: one recipient-language announcement plays to both people, then each hears a localized spoken go-ahead. Block both original microphones and translation/Guidance input until both legs acknowledge playback and both translation directions are ready; never substitute queue exhaustion or a browser-only mute for that gate. Startup failures close the call rather than falling back to plain calling; the existing mid-conversation fallback remains. `npm run prewarm:translation-disclosures` now prepares announcement, go-ahead, and failure clips; it uses paid APIs on cache misses and requires deliberate operator execution. See the runbook's protected-introduction section for rollout and live-listen acceptance.
- Voxandra remains a no-raw-audio-retention product by default. Do not add retained audio storage, playback, download, dashboard controls, pricing copy, settings, marketing copy, or public hints without explicit product direction; any future retained-audio design must separate transient transcription audio from customer-accessible private object storage with signed access and deletion lifecycle.

## Product And Copy Rules

- Prefer the product label `Call Records` for saved calls.
- Public landing copy should emphasize reviewed operational records, work threads, extracted details, action items, and team follow-through.
- The temporary mailing-list homepage has been retired. Do not re-add a public launch-list form, sign-up waitlist, or prelaunch CTA flow without explicit product direction.
- Keep landing examples B2B/operational. The current hero and How it works examples use a supplier payment release scenario; avoid drifting back to individual immigration/candidate examples unless the user asks.
- `PRICING_RATIONALE.md` is the reasoning behind every price, with the arithmetic, the measured cost figures, and the accepted trade-offs. **Read it before changing any price, rate, allowance, or margin constant** — most of those numbers are load-bearing for a reason recorded there. Update its change log when you change one.
- Pricing ladder is `Solo`, `Starter`, `Team`, `Operations`; `Team` is the featured `Most popular` plan (per `src/lib/pricing.ts`). `Calls only` remains a quiet secondary option because it does not include the live AI and reviewed-record features.
- Live Guidance and Live Translation are included **monthly on every paid plan** with metered overage. Plans differ by volume and seats, never by which features exist. Do not reintroduce "Team+", "Team and up", or one-time-trial copy for either feature; `npm test` counts the entitlement flags to catch a plan being re-gated instead of re-sized. Included minutes are sized to roughly 70-80% of what each plan's own calling credits buy at the US/CA retail rate, so both allowances run out together.
- **One credit balance covers everything usage-based**: call minutes plus Live Guidance and Live Translation past a plan's included minutes. Say so wherever more live minutes are discussed — the answer to "I need more" is "buy credits", never an add-on or a forced plan upgrade. Purchased top-up credits **never expire**; only the monthly credits included with a plan reset each cycle.
- Seats have **no direct cost**: every cost driver (included credits, Live Guidance and Live Translation minutes) is workspace-level, never per-seat. Widening `includedSeats` is therefore a reach decision, not a margin one. `includedSeats` is a hard ceiling — there is no mechanism to buy seats above it — so the numbers set where a team is forced to jump a plan. Do not treat per-seat price monotonicity as a design goal: the ladder differentiates on volume, Operations is capped at 12 because Enterprise is published as "13+ seats", and per-seat price rising at the top follows from both.
- Landing copy targets nine phone-heavy industries in three lanes — moving goods (freight forwarding & customs, import/export & sourcing, supplier & payment follow-up), moving deals (international sales & account management, customer onboarding & activation, compliance-heavy support), moving cases (relocation & immigration, insurance & claims, background verification). Keep lanes and examples in this frame.
- One primary CTA label across the landing: `Start a translated call` → `/login?redirect=/app/dialer`, always with a one-line "what happens next" beneath it. Default public copy still describes a free standard call. Carlos subsequently approved simplifying the translated trial to email sign-in and one 90-second call per eligible free workspace, with no SMS verification, separate daily trial budget, card or subscription. Only advertise the translated offer after the simplified code is deployed and live acceptance passes. See the translated-trial section below.
- Hero H1 is `Speak your language. Do business in theirs.` Supporting copy explains two-way translation, private prompts, and details captured for review. Keep the compact number-entry dialer; do not restore the oversized onscreen keypad or long decorative photo sections. The goods/deals/cases section uses three generated illustrative business photos, approved in the subsequent imagery request; see `docs/landing-imagery.md`.
- Banned marketing words in public customer copy (enforced case-insensitively by `npm test`): streamline, seamless, empower, unlock, revolutioni*, cutting-edge, best-in-class, world-class, leverage, supercharge, game-chang*. `Text-only`/`text-only` is also banned in landing components — Voice Translation is two-way *spoken* translation.
- Realtime rate constants come in pairs. `LIVE_COPILOT_*` and `TRANSLATED_CAPTIONS_*` overage must each stay at or above `REALTIME_MINIMUM_MARGIN_MULTIPLE` times their own cost estimate, or `assertRealtimeFeatureOverageMargin` throws **at call start**. Never edit a cost estimate without moving its overage rate in the same change; `npm test` enforces this arithmetically.
- Do not show raw model names, internal diagnostics, demo controls, or provider configuration in customer UI.

## Blog Posts (SEO/GEO)

- `/blog` is a first-party, typed-data-object blog — same pattern as `/compare`, no MDX/contentlayer. Canonical files:
  - `src/content/blog/types.ts`: the `BlogPostData` shape and the `BlogBlock` body union (`paragraph` / `heading` / `list` / `quote`).
  - `src/content/blog/posts/<slug>.ts`: one file per post.
  - `src/content/blog/posts.ts`: the registry (`allBlogPosts`, `getPublishedPosts()`, `getPostBySlug()`). `/blog`, `/blog/[slug]`, and `sitemap.ts` all read from here — add a post to this registry once and everything else (index listing, sitemap entry) follows automatically. Never hand-add a blog URL to `sitemap.ts`.
  - `src/components/blog/blog-post-page.tsx` and `blog-structured-data.tsx`: the shared post template and JSON-LD (BlogPosting + Blog/CollectionPage), mirroring `src/components/compare/`.
- Publishing is a deliberate, human-gated action, not something an agent decides alone. Every post has `status: "draft" | "published"`:
  - Draft posts render at their real `/blog/<slug>` URL locally (so they're previewable) but are excluded from `/blog`, `sitemap.xml`, and `generateStaticParams`, and get a `noindex, nofollow` robots meta tag.
  - Flipping `status` to `"published"` is the actual sign-off. Do this only when the user explicitly says the post is ready, as its own isolated one-line diff — never bundled into an unrelated change.
- Full workflow (topic → draft → iterate → publish) is scaffolded by the `new-blog-post` skill (`.claude/skills/new-blog-post/`) — use it rather than reinventing the steps.
- Hard constraints, learned expensively on this site (the FAQ accordion was invisible to GPTBot/ClaudeBot/PerplexityBot for weeks because answers only existed after a client-side click):
  - The full post body must be present in the server-rendered HTML on first load. No client-side-only rendering, no `"use client"` gating on body content, no collapsed/lazy content. Verify with `curl -s http://localhost:3000/blog/<slug> | grep '<some body text>'` — not just by looking in a browser.
  - Every post needs a visible published date and, once it's edited after publishing, a visible updated date.
  - Reuse this exact sentence verbatim wherever the product needs defining in blog copy — do not paraphrase it, LLMs converge on one canonical phrasing and paraphrases fragment that: "Voxandra is an AI platform for multilingual business calls. It translates both sides of live phone conversations, provides private guidance while people talk, and turns each call into a reviewed Call Record."
  - Never invent pricing, customer counts, or feature claims in blog copy. Cross-check any factual claim against `src/lib/pricing.ts` and the rest of this file before writing it.
- Research and topic grounding live outside this repo, in the `voxandra-marketing` repo at `~/Desktop/marketing/voxandra-marketing` (github.com/carlosmarcial/voxandra-marketing): `content/blog/` has the content brief template and topic backlog ("Good First Pages"), and `channels/seo/README.md` has the GEO research notes. Read those for context; never write to that repo from this one.

## MCP Server (Read-Only API Surface)

- `/api/mcp` is a stateless MCP Streamable HTTP endpoint (POST only) authenticated with `vx_`-prefixed personal API keys created in the `/app/mcp` section. Keys are stored hashed (`apiKeys` table); any member can create/revoke their own, owners/admins can revoke anyone's.
- `POST /mcp` is a transparent alias to `/api/mcp` (rewritten in `src/proxy.ts`, since many MCP clients try the conventional `/mcp` path by default). `GET /mcp` serves three representations by content negotiation: HTML docs page (default), Markdown (`Accept: text/markdown`), and the JSON server card (`Accept: application/json`). Keep all of them working if either the docs page or the API route moves.
- `src/lib/mcp/manifest.ts` builds the two public discovery documents — `/.well-known/mcp/server-card.json` (SEP-1649) and `/.well-known/mcp` (SEP-1960) — from the live server's own constants: protocol version from the MCP SDK, tool list from `MCP_TOOL_SUMMARIES`, instructions from `SERVER_INSTRUCTIONS`. Never hardcode those into the manifest; `npm test` asserts the advertised tool list matches the real contract exactly. `src/lib/mcp/tools-list.ts` is the dependency-free leaf holding `MCP_ENDPOINT_URL`, `MCP_SERVER_VERSION`, `SERVER_INSTRUCTIONS`, and the tool summaries — keep `node:`/Convex/SDK imports out of it so the manifests stay unit-testable.
- `/`, `/live-voice-translation`, `/mcp`, `/blog`, and `/blog/[slug]` support `Accept: text/markdown` content negotiation per acceptmarkdown.com (`src/lib/http/markdown-negotiation.ts`, wired in `src/proxy.ts`, Markdown rendered by `src/app/markdown/*`). A nonexistent path returns a real `404` — Markdown body for `Accept: text/markdown`, branded HTML otherwise — via the root catch-all `src/app/[...catchAll]/route.ts`; `src/app/not-found.tsx` handles in-app `notFound()` calls (HTML only). See `LOG.md` (2026-08-22) for the known Next.js `Vary`-header limitation on the default (non-negotiated) response.
- The MCP surface is v1 read-only by explicit product decision. Do not add write tools, call-placing tools, or billing-data exposure without explicit product direction — the agent-calling future goes through the `AGENTIC_FUTURE.md` gates, not this endpoint.
- `convex/mcp.ts` is the second sanctioned non-Convex-Auth data path (after the realtime worker): public Convex functions dual-guarded by `MCP_CONVEX_SECRET` plus the key hash, with the workspace always derived server-side from the key row via `requireMcpWorkspace`. Callers never supply a `workspaceId`.
- Every MCP response is field-projected in `convex/mcp.ts` following the `exportWorkspaceData` discipline: never expose billing/margin/cost fields, recording fields, provider identifiers, model/prompt names, or confidence/evidence internals. `caseId` is exposed as `threadId` (product language).
- Public tool names (`search_call_records`, `get_call_record`, `list_call_records`, `list_reminders`, `list_contacts`, `list_threads`, `get_thread`, `pre_call_brief`) are an external contract documented on `/mcp` — do not rename or remove them casually.
- Per-key rate limiting (120 req/min rolling window) and `lastUsedAt` tracking happen in `touchApiKeyUsage`, called once per HTTP request by the route. `/api/mcp` is excluded from the `src/proxy.ts` middleware matcher on purpose.
- MCP error responses must stay generic: fixed `ConvexError` codes in `convex/mcp.ts`, sanitized messages in `src/lib/mcp/server.ts`. Never leak stack traces, env var names, or table names.

## Architecture Rules

- Never trust client-provided `workspaceId`. Convex functions must derive workspace access server-side using auth context and helpers from `convex/authHelpers.ts`. (The MCP surface complies via `requireMcpWorkspace`, which derives the workspace from the API-key row inside Convex.)
- Anything only a cron, scheduler, or another Convex function calls must be `internalQuery`/`internalMutation`/`internalAction`, and `convex/crons.ts` must reference `internal.*` only. The Convex deployment URL is public in the browser bundle, so a public function with no guard is callable by anyone. `scripts/test-convex-function-visibility.mjs` (in `npm test`) enforces this file-by-file; a file whose public functions delegate auth to a guarded internal function must be added to its `DELEGATED_AUTH_FILES` allowlist with the reason.
- Hot-path queries must be bounded. Do not `.collect()` a whole workspace-scoped table (`calls`, `transcripts`, `aiMemories`, `extractedEntities`, `contacts`, `reminders`) in anything a page subscribes to; scan `calls` newest-first through `by_workspace_started` with a `take()` bound and join per row through `by_call`, or use a status-scoped index (`by_workspace_processing`, `by_review_pending`, reminders `by_status`). `scripts/test-bounded-list-queries.mjs` (in `npm test`) guards `convex/notes.ts`, `convex/transcripts.ts` and `convex/dashboard.ts`. Convex hard-caps one query at 16 MiB / 32k documents read.
- `processingStatus: "completed"` is terminal — a call that ended without AI capture (Calls-only plan, AI disabled, failed inbound forwarding). It is the dashboard's `completed` stage, never "processing".
- New workspace-scoped tables should include `workspaceId` and indexes that support workspace filtering.
- Keep destructive demo/seed/reset tools internal-only. They should not be client-callable from production user code.
- Do not store raw audio by default. Store metadata, transcripts, notes, extracted details, and run telemetry. Any raw-audio retention needs explicit product direction.
- Post-call transcription prefers **per-channel** attribution when Twilio returned two channels: `transcribeDualChannel` transcribes each leg separately so speakers come from the telephony channel rather than model diarization. It uses `gpt-4o-transcribe-diarize` per channel because that is the only model returning segment timestamps (`gpt-transcribe` supports only `json`/`text` — verified against the API), and two passes fit the existing `OPENAI_TRANSCRIPTION_COST_CENTS_PER_MINUTE` budget, so retail rates are unaffected. Labels stay the existing `A`/`B` vocabulary so `speakerMappings`, the extraction prompt, and the speaker-correction flow need no changes. Every failure path falls back to the single diarized pass and records `speakerAttribution: "diarization"` on the transcript — because raw audio is not retained, that field and the fallback log line are the **only** way to tell a working per-channel path from one that silently never activates.
- Provider webhooks do not use Convex Auth. Validate provider signatures/secrets in Next.js routes, then call guarded Convex mutations with webhook secrets.
- Translated-bridge transcription capture starts from Twilio-signed `stream-started` callbacks on `/api/twilio/status`, never inside the initial voice TwiML response or from the browser. `bridgeRecordings.claimBridgeRecording` deduplicates each leg and queues `twilioLifecycle.startBridgeRecording`, which checks provider state and reconciles existing recordings before bounded retries. Capture failure must not terminate the conversation; missing recordings become partial/unavailable Call Records. Behavioral regression coverage is in `scripts/test-twilio-bridge-lifecycle.mjs` (included in `npm test`).
- Twilio does **not** authenticate Media Stream WebSocket connections, so the realtime worker treats every `start` event as hostile until two checks pass: the TwiML routes' HMAC over the stream parameters (`REALTIME_STREAM_SIGNING_SECRET`, shared by Vercel and the worker only — never Convex) and a Convex call-SID binding (`realtimeRuntime.validateWorkerStreamStart`). Every `<Stream>` the app emits must go through `appendSignedStreamParameters` in `src/lib/twilio/server.ts`; `npm test` asserts no other `stream.parameter(` call exists. The signer is hand-mirrored between `src/lib/realtime/stream-signature.ts` and `scripts/realtime-media-worker-stream-auth.mjs` — change both together (the fixture test asserts byte-identical output). Deploy order for the secret is Vercel first, then the worker. See `REALTIME_WORKER_RUNBOOK.md` → "Media Stream Authentication".
- The retired launch-interest data remains in Convex for guarded export only. Do not reintroduce public launch-interest submissions without explicit product direction, and never send emails or free-text fields to PostHog.
- AI extraction prompt changes must update `AI_EXTRACTION_PROMPT_VERSION` in `src/lib/ai/extraction-prompt.ts` and be logged in `LOG.md`.
- PostHog must stay privacy-first: use `NEXT_PUBLIC_POSTHOG_HOST=https://eu.i.posthog.com`, expose only the browser-safe `NEXT_PUBLIC_POSTHOG_KEY`, and never capture emails, names, workspace names, phone numbers, transcripts, AI notes, contact names, billing IDs, provider IDs, or call content.
- PostHog event properties must remain coarse and whitelist-based through `src/lib/analytics.ts`; do not add raw customer content or identifiers beyond internal profile/workspace IDs and plan/subscription metadata.

## Commands

- Install deps with `npm install` if needed.
- Run static verification with `npm test` (`scripts/verify-multilingual-review.mjs`).
- Run focused browser-call lifecycle regressions with `node scripts/test-dialer-lifecycle.mjs` (also in `npm test`). It exercises the real dialer/provider handlers with mocked React hooks, Twilio, Convex, microphone access, and timers; no live calls or payments. Signed-in browser and real-audio acceptance are separate checks.
- Run lint with `npm run lint`. Existing warnings may appear in generated Convex files and a few legacy files; do not broaden them.
- Run production build with `npm run build`.
- Run whitespace checks with `git diff --check`.
- After Convex schema/function visibility/API changes, run `npx convex codegen`.
- For local UI checks, run `npm run dev` and open `http://localhost:3000`.

## Verification Expectations

- For frontend changes, browser-check desktop and mobile when practical, especially landing, dashboard, Call Records, call detail, wallet, settings, and reminders.
- For route changes, check both canonical and legacy redirects when relevant.
- For billing/calling changes, verify unauthenticated API routes still return `401` where appropriate, and avoid making real calls or payment actions unless explicitly requested.
- For analytics changes, verify PostHog still initializes against the EU host, session replay/autocapture remain disabled, and static privacy guards in `npm test` still cover forbidden customer-content properties.
- For Convex changes, check generated API types and use workspace-scoped functions.
- Before finalizing, run at least the relevant subset of `npm test`, `npm run lint`, `npm run build`, and `git diff --check`; explain anything not run.

## Git And Repo Hygiene

- The repo may contain user changes. Do not revert files you did not intentionally modify.
- Work directly on `master`. Do not create feature branches or PR branches for this repo unless the user explicitly asks for one.
- When asked to commit/push, commit on `master` and push directly to `origin/master`.
- Do not commit `.env*`, local credentials, generated build output, or large local test assets.
- `next-env.d.ts` should import `./.next/types/routes.d.ts`; Next dev can sometimes rewrite it to `./.next/dev/types/routes.d.ts`. Restore the committed form if it changes during local dev.
- Convex `_generated` files should only change as a result of `npx convex codegen`.
- Outside contributions need a signed contributor license agreement (`ICLA.md` or `CCLA.md`) before merging; `.github/workflows/cla.yml` asks for it on each pull request and stores signatures on the `cla-signatures` branch. Never edit that branch or its signature file by hand, and never merge a pull request whose CLA check has not passed.
- Keep `LOG.md` updated for meaningful product, architecture, billing, AI, or navigation changes.

## UX Guardrails

- Customer Settings should stay small and actionable.
- Dashboard is not an archive page; it should answer what just happened and what to do next.
- Call Records is the archive/search surface.
- Avoid form-heavy CRM patterns. Contacts, threads, reminders, and extracted details should feel like memory created from calls, not manual database entry.
- Use existing visual language: warm off-white backgrounds, restrained violet brand accents, green success states, compact product cards, and practical B2B examples.
- Keep responsive layouts free of horizontal overflow. Text inside cards/buttons must fit cleanly on mobile and desktop.
